# rms-engine

Движок системы управления требованиями: общая тема сайта, скрипты CI и общий workflow сборки для всех репозиториев
продуктов предприятия (подход Documentation as Code, сайт на Zensical).

В репозитории продукта лежат только данные — документы аналитиков (`docs/`) и собственные значения продукта
в `zensical.toml` (название сайта, адреса, трекер). Все остальные настройки берутся из движка.
Когда аналитик отправляет изменения в `main` продукта, его короткий workflow вызывает общий workflow движка: тот
скачивает движок, пересчитывает версии, статусы, меню и дашборд, собирает сайт и публикует его на GitHub Pages продукта.
Исправление в движке получают все продукты при следующей сборке.

## Структура

| Каталог | Содержимое |
|---|---|
| `custom/` | Тема сайта (`custom_dir`): шаблоны `main.html` и `passport.html`, стили `css/extra.css`, скрипты страниц `js/` |
| `zensical.base.toml` | Общие настройки сайта всех продуктов: тема, возможности, шрифты, цветовые схемы, расширения Markdown |
| `py/` | Скрипты CI (см. «Скрипты»); общая логика — `common.py`, настройки по умолчанию — `config.py` |
| `.github/workflows/build.yml` | Общий workflow: генерация, коммит, сборка, публикация (вызывается из продуктов) |
| `templates/product/` | Заготовки для нового продукта: `ci.yml`, `zensical.toml`, `.gitignore` |

В файлах `custom/css/*` и `custom/js/*` нельзя писать двойную фигурную скобку, фигурную скобку с процентом и фигурную
скобку с решёткой: они подключаются как шаблоны Jinja.

## Подключение продукта

1. Скопируйте в репозиторий продукта заготовки из `templates/product/`:
   * `ci.yml` → `.github/workflows/ci.yml`;
   * `zensical.toml` → `zensical.toml` — замените название сайта, `site_url`, `repo_url`, адрес трекера; маркеры
     `BEGIN/END GENERATED NAV` и `BEGIN/END ENGINE SETTINGS` оставьте: блоки между ними заполнит движок;
   * `.gitignore` → `.gitignore` (в нём `engine/`: движок в коммиты продукта не попадает).
2. Разложите документы по стандартной структуре `docs/` (см. «Стандартная структура docs/»).
3. В настройках репозитория продукта: **Settings → Pages → Source: GitHub Actions**.
4. Отправьте изменения в `main` — сборка запустится сама.

Если в продукте уже есть история git (документы перенесены из другого репозитория вместе с историей), версии и журналы
изменений сохранятся. В новом репозитории без истории все версии начнутся с `0.00.00`.

## Версии движка

Продукт подключает движок по тегу: `uses: DmitryKhilko/rms-engine/.github/workflows/build.yml@v1` и
`engine_ref: v1` (в обеих строках — одна и та же версия).

* Каждый выпуск получает точный тег `vX.Y.Z` (например, `v1.0.0`, `v1.1.0`).
* Плавающий тег `v1` всегда указывает на последний выпуск первой линейки: продукты на `@v1` получают исправления
  автоматически.
* Изменения, требующие правок в продуктах (другая структура `docs/`, другой формат данных), выпускаются
  как `v2`; продукты переходят на неё сами, меняя `v1` на `v2`.

Выпуск версии:

```sh
git tag v1.0.0
git tag -f v1            # перенести плавающий тег на новый выпуск
git push origin v1.0.0
git push -f origin v1
```

**Если репозиторий движка приватный:** в его настройках разрешите доступ к workflow (**Settings → Actions → General →
Access → Accessible from repositories owned by …**) и заведите токен с правом чтения содержимого движка (fine-grained
token или токен GitHub App) в секретах продукта или организации; в `ci.yml` продукта раскомментируйте блок `secrets`.
Для публичного движка ничего этого не нужно.

## Локальный просмотр сайта продукта

В корне репозитория продукта:

```sh
git clone --depth 1 --branch v1 https://github.com/DmitryKhilko/rms-engine engine
pip install zensical -r engine/py/requirements.txt
zensical serve
```

Для диаграмм PlantUML нужны установленные PlantUML (команда `plantuml`) и Graphviz. Обновить движок:
`git -C engine pull`.
Запустить скрипт локально (из корня продукта): `python engine/py/nav.py --check`.

## Скрипты

Скрипты лежат в `py/` и запускаются из корня репозитория продукта (корень — текущая папка или переменная окружения
`RMS_PRODUCT_ROOT`). В CI они идут по порядку:

| Скрипт | Что делает |
|---|---|
| `site_settings.py` | Общие настройки сайта в `zensical.toml` продукта (из `zensical.base.toml`) |
| `changelog.py` | Версии и «Журнал изменений» разделов по истории git |
| `status.py` | Поля `priority`, `status` (F и SF) и `icon` (только SF) в метаданных |
| `nav.py` | Меню сайта (блок `nav` в `zensical.toml` продукта) |
| `dashboard.py` | Дашборд на странице «Требования к продукту» |

Общая логика — `common.py`: чтение и запись файлов с сохранением концов строк (LF или CRLF), запись поля в метаданные,
обход реестра (фичи и их SF в порядке меню, вычисление статуса и приоритета F). Все настраиваемые значения — в
`config.py`; в остальных файлах только логика. Сторонние пакеты скриптам не нужны (стандартная библиотека Python 3.11+
и git). Любой скрипт можно запустить с ключом `--check`: он ничего не записывает и завершается с кодом 1, если
сформированные файлы устарели.

## Общие настройки сайта

Тема (`custom_dir = "engine/custom"`), язык, логотип, возможности, шрифты, цветовые схемы и все расширения Markdown
(PlantUML, вставка файлов, иконки, предпросмотр ссылок, GLightbox и др.) одни для всех продуктов и хранятся в
`zensical.base.toml` движка. При каждой сборке продукта `py/site_settings.py` переписывает этим файлом блок между
маркерами `# BEGIN ENGINE SETTINGS …` и `# END ENGINE SETTINGS` в `zensical.toml` продукта, а CI коммитит результат —
поэтому в репозитории продукта всегда полный `zensical.toml`, и локальный просмотр работает без дополнительных шагов.

* **Поменять настройку для всех продуктов** — исправить `zensical.base.toml` и выпустить версию движка. Продукт получит
  её при своей следующей сборке (после очередного push, ручного запуска или по расписанию — в `ci.yml` продукта есть
  закомментированная еженедельная сборка).
* **В `zensical.toml` продукта** остаются только его собственные значения: раздел `[project]` (название сайта, адреса,
  автор) — до блока; таблицы продукта (например, `[project.extra.tracker]` с адресом трекера) — после блока, каждая со
  своим заголовком. Повторять в продукте таблицу из общих настроек нельзя: TOML не допускает одну таблицу дважды —
  скрипт сообщит об ошибке и не изменит файл.
* **Логотип и значок вкладки** — файл `docs/assets/logo.png` продукта (путь задан в общих настройках).

## Стандартная структура docs/

Значения в `py/config.py` — общий стандарт предприятия: структура `docs/`, неизменная часть меню, статусы, значки,
приоритеты, правила версий и проверок, названия папок и файлов в меню. В репозитории продукта настроек скриптов нет:
чтобы изменить стандарт, правят `py/config.py` движка, и изменение получают все продукты.

| Путь в `docs/` | Пункт меню |
|---|---|
| `index.md` | О продукте |
| `project/index.md` | Проект |
| `requirements/business-context/glossary.md` | Требования → Глоссарий |
| `requirements/business-context/business-requirements.md` | Требования → Бизнес-требования |
| `requirements/features/index.md` | Требования → Требования к продукту (страница группы с дашбордом) |
| `requirements/global/index.md` | … → Глобальные требования (страница группы) |
| `requirements/global/design-system/index.md` | … → Глобальные требования → Дизайн-система |
| `requirements/global/ar.md`, `nfr.md`, `sr.md` | … → Глобальные AR, Глобальные NFR, Глобальные SR |
| `requirements/global/sf-g-*/` | … → Глобальные требования → глобальные функциональности (после SR, без своей группы) |
| `requirements/features/*/` | Требования → Требования к продукту → фичи (после «Глобальных требований») |
| `requirements-archive/index.md` | Архив |
| `assets/logo.png` | Логотип и значок вкладки |

Все страницы необязательны: страницы, которой у продукта нет, нет и в меню; группа без страниц не выводится.

## Меню сайта

Меню (блок `nav` в `zensical.toml` продукта между маркерами `BEGIN/END GENERATED NAV`) вручную не правят: его после
каждого слияния в `main` пересобирает `py/nav.py`.

* **Неизменная часть меню** («О продукте», «Проект», «Глоссарий», «Архив» и т. д.) — стандартная структура `docs/`
  (см. выше).
* **«Требования к продукту»** — щелчок открывает страницу `requirements/features/index.md` с дашбордом. Первым пунктом
  группы идут «Глобальные требования», за ними — фичи: каждая подпапка `requirements/features/` с `index.md`.
  * Название фичи — текст после ID в заголовке требования F в её `index.md`: из `## F-PT. Справочник видов изделий`
    берётся «Справочник видов изделий». Если такого заголовка нет, берётся заголовок первого уровня, и скрипт выводит
    предупреждение.
  * Порядок фич — поле `order` в метаданных их `index.md` (меньше — выше), без него — после, по имени папки.
  * Подпапки фичи подписываются по словарю папок (`sf-create` → «Создание», `sf-list` → «Список», …), файлы — по
    словарю файлов (`dr.md` → «DR», `fr.md` → «FR», …). Файлы прямо в папке фичи получают приставку «Общие»
    («Общие UC»). Порядок пунктов — порядок записей в словаре.
  * Папка `sf-*`, которой нет в словаре, подписывается текстом после ID в заголовке SF её `index.md`
    (`## SF-PT-EXPORT. Выгрузка` → «Выгрузка») и идёт после стандартных. Остальные папки и файлы не из словаря
    попадают в меню под своим именем, а скрипт выводит предупреждение. Папки без `.md`-файлов (например, `api/`)
    в меню не попадают.
* **Глобальные функциональности** — папки `requirements/global/sf-g-*` с файлом `index.md`. В меню они идут прямо
  в группе «Глобальные требования», после «Глобальные SR», без своей группы. Название — текст после ID
  в заголовке SF их `index.md` (`## SF-G-PAG. Пагинация` → «Пагинация»). Порядок — поле `order` в метаданных их
  `index.md` (меньше — выше, как у фич), без него — после, по имени папки.

## Статусы, значки и приоритеты

Статус подфункциональности (SF) аналитик вписывает **вручную** в `index.md` папки `sf-*`, строкой
`- **Статус**: анализ`. Допустимые значения: бэклог, анализ, готово к разработке, разработка, реализовано, архив
(регистр не важен). Поля `status` и `icon` в метаданных вручную не правят: их обновляет `py/status.py`.

В `status` записывается то же русское название (его выводит «паспорт» страницы), в `icon` — значок в левом меню:

| Статус | `icon` (значок в левом меню) |
|---|---|
| бэклог | `lucide/file` |
| анализ | `lucide/file-pen-line` |
| готово к разработке | `lucide/file-check` |
| разработка | `lucide/file-braces` |
| реализовано | `lucide/file-text` |
| архив | `lucide/file-archive` |

**Статус фичи (F)** не вписывают вручную: скрипт вычисляет его по статусам её SF по правилу Jira для эпиков. SF в архиве
не учитываются, а по остальным:

| Статусы SF | `status` фичи |
|---|---|
| все в бэклоге | `"бэклог"` |
| все реализованы | `"реализовано"` |
| любое другое сочетание | `"в работе"` |
| все SF в архиве | `"архив"` |

Статус «в работе» бывает только у F: в SF его вписать нельзя (скрипт сообщит об ошибке). Статус F выводит паспорт
её страницы и дашборд. Поля `icon` у F нет: в левом меню значок только у SF, фича выглядит как обычная группа.

**Приоритет SF** аналитик вписывает вручную строкой `- **Приоритет**: must` (must, should, could, won't). Скрипт
записывает его в поле `priority` — первой строкой метаданных. **Приоритет F** вычисляется: самый строгий приоритет
среди её SF (must строже should и т. д.; SF в архиве не учитываются, если есть другие). В тексте F строку «Приоритет»
не ведут. Значение не из списка — ошибка; строки нет — предупреждение, а дашборд покажет SF в «Требует внимания».

**«Паспорт» страницы** (`custom/passport.html`) выводит приоритет, статус, редактора, версию, задачу, релиз и дату
релиза из метаданных страницы.

## Дашборд требований к продукту

Страницу `requirements/features/index.md` после каждого слияния в `main` дополняет `py/dashboard.py`. Дашборд
записывается между маркерами `<!-- BEGIN GENERATED DASHBOARD … -->` и `<!-- END GENERATED DASHBOARD -->` (если их нет —
сразу после заголовка первого уровня); текст страницы вне маркеров ведут вручную.

* **Прогресс по F** — полоса на каждую F: доля её SF в каждом статусе и «реализовано X из N».
* **Приоритет × статус SF** — сколько SF каждого приоритета в каждом статусе.
* **Требует внимания** — проверки: SF без FR, FR без критериев приёмки (блока `gherkin`), SF без приоритета,
  повторяющиеся коды требований, неподтверждённые вопросы и допущения, битые ссылки. Выводятся все замечания,
  каждое — со ссылкой на место в требованиях (SF, раздел требования, вопроса или допущения). Коды, вопросы,
  допущения и ссылки проверяются в глобальных требованиях и в фичах.
  * Вопрос (`….Q01`) не попадает в список в статусе «закрыт», допущение (`….H01`) — в статусах «принято»,
    «подтверждено», «отвергнуто» (`NOTE_FINAL` в `py/config.py`).
* **Последние изменения** — все записи журналов изменений глобальных требований и фич за последние 10 календарных
  дней, считая день сборки (`CHANGES_DAYS`, `CHANGES_TIMEZONE` в `py/config.py`); версия — ссылка на коммит.
  Устаревшие записи уходят с дашборда при следующей сборке.

Оформление — `custom/css/extra.css`, раздел 12.

## Версии и журнал изменений разделов

Версию раздела и «Журнал изменений» вручную не правят: их пересчитывает `py/changelog.py` по истории git продукта.

* **Где ведётся журнал.** Только в `index.md` с заголовком `## Журнал изменений {#change-history .collapsed}`.
* **Чьи коммиты попадают в журнал.** Такой `index.md` отвечает за свою папку: в журнал попадает коммит, изменивший
  любой файл папки и её подпапок (в том числе `api/*.json`), кроме подпапок с собственным `index.md` с журналом.
* **Запись журнала** (новые сверху): `Версия 0.01.00 (04.11.2026 07:44:15; dr.md). Редактор: Автор`, где текст
  в квадратных скобках — ссылка на коммит (адрес — `repo_url` из `zensical.toml` продукта). После даты перечислены
  изменённые файлы раздела — пути относительно папки `index.md`.
* **Метаданные.** Если в метаданных `index.md` есть поле `version`, скрипт обновляет `version`, `version_datetime`
  (`ДД.ММ.ГГГГ ЧЧ:ММ:СС`) и `editor` (автор коммита).

Удобно менять и коммитить файлы по одному: тогда каждая запись журнала соответствует одной правке. Версия `X.YY.ZZ`
считается по префиксу сообщения коммита (Conventional Commits):

| Сообщение коммита | Что произойдёт |
|---|---|
| `fix: …`, `docs: …` или сообщение без префикса | `0.01.00` → `0.01.01` |
| `feat: …` | `0.01.01` → `0.02.00` |
| `feat!: …` или `BREAKING CHANGE` в тексте | `0.02.00` → `1.00.00` |
| `draft: …` | версия, редактор и журнал не меняются |

Первый коммит папки — создание раздела: версия `0.00.00`, записи в журнале нет. Коммиты CI с пометкой `[skip ci]` не
учитываются. Если переименовать или перенести папку раздела, история до переноса в версию не попадёт.
